# بنيان الرياضيات

منصة تعليمية عربية RTL للرياضيات — حسابات حقيقية (معلم واحدة وطلابها) عبر
Supabase. للطالب: تعلّم، اكتشف، تدرّب، العب، شاراتي، هويتي ووطني، مبادرة
القائد الرقمي. للمعلم: لوحة فيها إدارة الطلاب والمهام ولوحة النجوم المرحة ونتائج
«اكتشف»، و«اختبر» (المرحلة الثانية)، وأربع ألعاب في «ألعب» — الجمع والطرح والتقريب والضعف (المرحلة الثالثة، مُحدَّثة). (بقية أقسام «ألعب» الأربعة و«تنمية المهارات» غير مبنية بعد.) **«المسابقات»** (المرحلة التاسعة): منشئ مسابقات مفتوحة برابط عام بلا حساب، مستقل عن نجوم الطلاب وشاراتهم — شغّل `supabase/phase9-competitions.sql` مرة واحدة في SQL Editor لتفعيله.

---

## ⭐ ابدأ من هنا بعد فك الـZIP (v39)

1. افتح Terminal **داخل** مجلد `bunyan-math` ثم نفّذي: `npm install`
2. انسخي `.env.example` إلى `.env` وضع فيه `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`.
3. في Supabase → SQL Editor شغّل الملفات **بهذا الترتيب** (كل واحد مرة واحدة، وكلها آمنة للإعادة):
   `supabase/schema.sql` ← `supabase/game_bank.sql` ← `phase8-fun-games.sql` ← `phase9-competitions.sql` ← `phase9b-competition-attachments.sql` ← `phase10-demo-mode.sql`
4. انشر الدوال: `supabase functions deploy create-student` و`delete-student`، ثم
   `supabase functions deploy demo-start --no-verify-jwt` و`supabase functions deploy demo-sweep --no-verify-jwt`.
   **مهم:** أعد نشر `demo-start` و`demo-sweep` حتى لو نشرتِهما سابقًا (تشتركان في `_shared/demo.ts`).
5. فعّلي التجربة: `update public.demo_settings set enabled = true;`
   وإن بقيت حسابات تجربة قديمة بدور خاطئ: شغّل `supabase/demo-cleanup-orphans.sql` ثم `{"action":"teardown_all"}` لدالة `demo-sweep` لتبدأ Slots جديدة.
6. `npm run build` ثم `npm run dev`، وجرّب: دخول المعلم، دخول الطالب، «تجربة المعلم»، «تجربة الطالب».

**تنبيه اختبار:** المتصفح يشارك جلسة الدخول بين كل التبويبات. لا تجرّبي «تجربة المعلم» في تبويب و«تجربة الطالب» في تبويب آخر من نفس المتصفح (آخر دخول يغيّر الجلسة في التبويبين!). استخدمي نافذة خاصة (Incognito) أو متصفحًا آخر للدور الثاني.

**ما تغيّر في v39:** صورة هيرو المعلم أُعيد تفريغها (كانت الخلفية رقعة شطرنج مرسومة داخل الصورة فقصّت الحجاب والرداء)،
وإصلاح `AuthContext` (كان يعيد تحميل الصفحة ويصفّر ما تفعله المعلم عند العودة للتبويب، ويحتفظ ببروفايل قديم لحظة تبديل الحساب)،
وصفحة الدخول صارت تتحقق من دور حساب التجربة قبل التوجيه وتُظهر رسالة واضحة بدل الدخول لصفحة الدور الخطأ.

## خامسًا: إعداد Supabase (المرة الأولى فقط)

### 1. إنشاء المشروع في Supabase

1. ادخل إلى [supabase.com](https://supabase.com) وسجّل الدخول.
2. اضغط **New Project**.
3. اختر اسمًا (مثلًا `bunyan-al-riyadiyat`) وكلمة مرور لقاعدة البيانات
   (احفظها في مكان آمن) ومنطقة قريبة منك، ثم **Create new project**.
4. انتظر دقيقة أو دقيقتين حتى يجهز المشروع.

### 2. تنفيذ ملف قاعدة البيانات (SQL)

1. من القائمة الجانبية اليسرى داخل مشروعك: اضغط **SQL Editor**.
2. اضغط **New query**.
3. افتح الملف `supabase/schema.sql` الموجود داخل مجلد المشروع، انسخ **كل
   محتواه**، والصقه في المحرر.
4. اضغط **Run** (أو Ctrl/Cmd + Enter).
5. يجب أن تظهر رسالة نجاح بدون أخطاء. هذا الملف الواحد ينشئ كل شيء: الجداول
   (`profiles`, `classes`, `teachers`, `students`, `tasks`, `task_assignments`,
   `badges`, `student_badges`, `placement_questions`, `placement_attempts`,
   `placement_attempt_questions`, `lesson_completions`, `star_board_entries`)،
   ويفعّل الصلاحيات (Row Level Security) عليها، وينشئ الدوال، وبنك أسئلة «اكتشف»،
   وكتالوج الشارات.
6. الملفان `supabase/discover_and_lessons_migration.sql` و
   `supabase/star_board_migration.sql` مقتطفان من `schema.sql` نفسه، ولا حاجة
   لتشغيلهما إن شغّلت `schema.sql` كاملًا. هما فقط لمشروع Supabase قائم شُغِّلت
   عليه نسخة أقدم من `schema.sql`.

### 3. الحصول على مفاتيح الربط (Project URL و anon key)

1. من القائمة الجانبية: **Project Settings** (أيقونة الترس) -> **API**.
2. ستجد:
   - **Project URL** — رابط يشبه `https://xxxxxxxx.supabase.co`.
   - **Project API keys** -> **anon public** — مفتاح طويل يبدأ عادة بـ
     `eyJ...`.
3. انسخ القيمتين، ستحتاجهما في الخطوة التالية.

### 4. إنشاء ملف `.env`

1. داخل مجلد المشروع، انسخ الملف `.env.example` وأعد تسميته إلى `.env`
   (نفس المجلد، بجانب `package.json`).
2. افتحه وضع القيم الحقيقية:

```bash
VITE_SUPABASE_URL=https://xxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJ....(المفتاح الكامل)
```

3. احفظ الملف. **لا تشارك هذا الملف مع أحد ولا ترفعه إلى GitHub** (هو
   مستثنى تلقائيًا في `.gitignore`).

### 5. إنشاء حساب معلم تجريبي

1. من القائمة الجانبية في Supabase: **Authentication** -> **Users**.
2. اضغط **Add user** -> **Create new user**.
3. أدخل بريدًا إلكترونيًا وكلمة مرور، وتأكد أن **Auto Confirm User** مفعّل
   (حتى لا تحتاج تفعيل البريد يدويًا).
4. **مهم جدًا**: قبل الضغط على Create، افتح قسم **User Metadata** (أو
   عدّله بعد الإنشاء من صفحة المستخدم -> Edit) وأضف:

```json
{ "role": "teacher", "full_name": "الأستاذة سارة" }
```

5. اضغط Create user. هذا يُنشئ تلقائيًا (عبر trigger موجود في `schema.sql`)
   صفًا في `profiles` بالدور `teacher`، وصفًا في `teachers`، وصفًا واحدًا لها
   في `classes` باسم «صفي».

### 6. الصف

لا توجد خطوة هنا: الصف يُنشأ تلقائيًا مع حساب المعلم (الخطوة السابقة)، ولوحة
المعلم تنشئه أيضًا إن لم تجده. **لا تُضيفي صفًا يدويًا بـSQL**: لوحة المعلم
والدالة `create-student` تقرآن صفًا واحدًا فقط لكل معلم.

### 7. إضافة الطلاب

الطلاب يُضافون من **لوحة المعلم** (زر «إضافة طالب»)، وتُنشئ الدالة
`create-student` حساب الطالب وتُرجع **رمز الدخول** البسيط (أول حرفين من اسم الطالب + رقمان، مثل `Mo-12` لمحمد و`Na-34` لناصر؛ والرموز السابقة `BNY1` و`BNY-XXXXX` ما زالت تعمل) الذي يدخل
به الطالب من تبويب «دخول الطالب». هذه الدالة (وكذلك `delete-student`) تحتاج نشرًا
مرة واحدة على مشروعك بواسطة Supabase CLI:

```bash
supabase functions deploy create-student
supabase functions deploy delete-student
```

ملاحظة: لم تُنشر هاتان الدالتان ولم تُختبرا على مشروع حي بعد.

طريقة يدوية قديمة (بدون الدالة): أضف مستخدمًا من Authentication -> Users مع
User Metadata `{ "role": "student", "full_name": "سارة أحمد" }`، ثم اربطيه بالصف
بـSQL (`update public.students set class_id = ... where id = ...`). هذا الطالب
ليس له رمز دخول، فيدخل بالبريد وكلمة المرور من تبويب «دخول المعلم» (تبويب
الطالب يقبل الرمز فقط) ويُحوَّل تلقائيًا إلى صفحة الطالب.

### 8. التأكد أن الجداول والسياسات موجودة فعليًا

- **Table Editor** (من القائمة الجانبية) -> يجب أن ترى الجداول الثلاثة عشر
  المذكورة في الخطوة 2 (`profiles`, `classes`, `teachers`, `students`, `tasks`،
  ... إلخ).
- افتح أي جدول منها واضغط على أيقونة **RLS** أعلى الجدول — يجب أن تكون
  الحالة "Enabled" مع قائمة السياسات (Policies) التي أنشأها `schema.sql`.

## سابعًا: ماذا يجب أن أرى

- فتح `http://localhost:5173` يوجّهك تلقائيًا إلى `http://localhost:5173/login`
  (صفحة تسجيل الدخول، بهوية المنصة، عربية RTL، وفيها تبويبان: «دخول المعلم»
  بالبريد وكلمة المرور، و«دخول الطالب» برمز الدخول).
- إن لم يكن `.env` مضبوطًا بعد، ستظهر رسالة صفراء توضح أن Supabase غير
  مربوط — الصفحة تعمل بصريًا لكن الدخول الفعلي لن ينجح حتى تربطه.

---

## ثامنًا: اختبار حساب المعلم

1. في `/login` أدخل بريد وكلمة مرور حساب المعلم الذي أنشأته في الخطوة
   الخامسة-5.
2. اضغط **دخول**.
3. يجب أن تُنقل تلقائيًا إلى `http://localhost:5173/teacher` وترى:
   - ترحيبًا باسمها.
   - اسم الصف (قابل للتعديل).
   - عدد الطلاب (بعد إضافة طلاب).
   - لوحة النجوم المرحة، ومهام الأسبوع، وقائمة الطلاب (الاسم، رمز الدخول،
     المهام المكتملة، الشارات، النقاط)، وقسم نتائج «اكتشف».
4. اضغط **تسجيل الخروج** أعلى الصفحة — يجب أن تعود إلى `/login`.

---

## تاسعًا: اختبار حساب الطالب

1. سجّل خروج المعلم إن كانت لا تزال مسجّلة دخول.
2. في `/login` اختر تبويب «دخول الطالب» وأدخل رمز الدخول الذي ظهر عند إضافة الطالب.
3. يجب أن تُنقل تلقائيًا إلى `http://localhost:5173/student` وترى الصفحة
   الرئيسية (الترحيب باسمه، النقاط، البطاقات الخمس، مهام الأسبوع، شاراتي،
   مستواي في الرياضيات، آخر نشاط).
4. اسم الطالب والنقاط المعروضة في أعلى الصفحة هي بيانات حقيقية قادمة من قاعدة
   البيانات. إن لم توجد بيانات (مهام أو شارات أو نشاط) تظهر قيم صفرية وقوائم
   فارغة، وليس بيانات تجريبية.

## عاشرًا: اختبار الصلاحيات (الأهم)

### اختبار 1 — طالب يحاول الوصول للوحة المعلم عبر الرابط مباشرة

1. سجّل الدخول كطالب.
2. بينما أنت مسجَّل دخول كطالب، غيّر الرابط يدويًا في المتصفح إلى:
   `http://localhost:5173/teacher`
3. **النتيجة المتوقعة**: يتم إعادة توجيهك فورًا إلى `/student` — لا تُعرض
   لك لوحة المعلم إطلاقًا، ولو للحظة.

### اختبار 2 — مستخدم غير مسجّل دخول يحاول فتح أي لوحة مباشرة

1. سجّل الخروج تمامًا.
2. افتح `http://localhost:5173/teacher` أو `/student` مباشرة.
3. **النتيجة المتوقعة**: تحويل فوري إلى `/login`.

### اختبار 3 — Row Level Security فعليًا (وليس فقط الواجهة)

هذا الاختبار يتحقق من أن الحماية موجودة في **قاعدة البيانات نفسها**، وليست
مجرد إخفاء في الواجهة (وهو الفرق الجوهري الذي طلبته):

1. في Supabase: **SQL Editor**.
2. نفّذ هذا الاستعلام وأنت "بصفتك" الخدمة (service role) — لاحظ أنه ناجح
   دائمًا من هنا لأن SQL Editor يتجاوز RLS، هذا طبيعي وللمقارنة فقط:
   ```sql
   select * from public.students;
   ```
   سترى كل الطلاب — هذا متوقع من داخل لوحة Supabase نفسها.
3. الاختبار الحقيقي هو من **داخل التطبيق**: افتح Developer Tools في
   المتصفح (F12) -> تبويب Console وأنت مسجّل دخول كطالب، ثم نفّذ يدويًا (إن
   رغبت في اختبار متقدم) استعلامًا يحاول قراءة كل جدول الطلاب — ستجده يعيد
   صفّك أنت فقط، وليس بقية الطلاب، مهما حاولت — لأن RLS تمنع ذلك من جهة
   الخادم نفسه، بغض النظر عمّا يفعله الكود في المتصفح.
4. أبسط تأكيد عملي: أنشئ طالبين مختلفين (كما في الخطوة الخامسة-7)، سجّل
   دخول بحساب الطالب الأول — لن ترى أي بيانات عن الطالب الثاني في أي مكان
   بالواجهة، لأن الاستعلامات نفسها (`students`, `profiles`) محكومة بـ
   `id = auth.uid()`.

## ماذا أفعل إذا ظهر خطأ أثناء التشغيل

| الخطأ | السبب المحتمل | الحل |
|---|---|---|
| صفحة بيضاء أو خطأ "Failed to fetch" عند الدخول | `.env` غير موجود أو القيم خاطئة | تأكد من وجود `.env` بجانب `package.json` وأن القيم صحيحة، ثم أعد تشغيل `npm run dev` (يجب إعادة التشغيل بعد أي تعديل في `.env`) |
| "البريد الإلكتروني أو كلمة المرور غير صحيحة" | المستخدم غير موجود أو لم يُفعَّل | تأكد من إنشائه في Authentication -> Users وأن Auto Confirm كان مفعّلًا |
| المعلم تسجل دخول لكن لا ترى طلابًا | لم تُضَف طلاب بعد (أو طالب أُنشئ يدويًا ولم يُربط بالصف) | أضف الطلاب من لوحة المعلم (زر «إضافة طالب»)، أو اربطي الطالب اليدوي بـ`update public.students set class_id = ...` |
| رسالة «تعذّر تحميل بيانات الحساب» بعد تسجيل الدخول | الجلسة موجودة لكن صف المستخدم في `profiles` غير موجود أو تعذّر تحميله | تأكد من وجود صف للمستخدم في `profiles` (يُنشأ بالـtrigger عند إنشاء المستخدم)، ثم «إعادة المحاولة» |
| زر «إضافة طالب» يفشل | الدالة `create-student` لم تُنشر بعد على Supabase | `supabase functions deploy create-student` (وكذلك `delete-student`) |
| خطأ متعلق بـ `role` غير معروف بعد تسجيل حساب جديد | لم تُمرَّر `role` في User Metadata عند الإنشاء | عدّل المستخدم من Authentication -> Users -> اختر المستخدم -> عدّل User Metadata يدويًا، ثم أعد تسجيل الدخول |
| `npm install` يفشل | مشكلة اتصال بالإنترنت أو نسخة Node قديمة | تأكد من الاتصال بالإنترنت ومن أن `node -v` يظهر 18 أو أعلى |

## هيكل المشروع (محدَّث)

```
src/
  assets/            الشعار، الأيقونات، صور Hero
  components/        مكوّنات الواجهة (Sidebar, TopBar, Hero, البطاقات...)
  components/auth/   ProtectedRoute — حارس المسارات الفعلي
  components/teacher/  مكوّنات لوحة المعلم (نوافذ الطلاب والمهام، لوحة النجوم...)
  components/discover/ مكوّنات اختبار «اكتشف»
  components/lessons/  مكوّنات «تعلّم» (البطاقات ومشغّل الفيديو)
  components/practice/ بطاقات «تدرّب» و«العب»
  context/           AuthContext — حالة تسجيل الدخول والبروفايل
  data/              قوائم ثابتة: الدروس، الألعاب، أوراق التدريب، المبادرات، التنقل
  lib/               عميل Supabase + أنواع قاعدة البيانات + منطق اكتشف/النجوم/الدروس
  pages/             صفحات الطالب (الرئيسية، تعلّم، اكتشف، تدرّب، العب، شاراتي،
                     الإعدادات، المبادرات) + LoginPage + TeacherDashboardPage
```

## 🧱 المرحلة الثانية — «اختبر» ونتائجه عند المعلم ولوحة النجوم

**ما الجديد**
- **اختبر** (`/quiz`): عشرة أسئلة بنفس مهارات ومستوى «اكتشف» لكن بأرقام جديدة في
  كل محاولة، بلا رفع في الجمع ولا استلاف في الطرح. تصميم «ابنِ برجك» (كل إجابة
  صحيحة تضع طوبة) مع أصوات وزر كتم.
- **نفس نظام «اكتشف»**: الأسئلة والإجابات الصحيحة والنتيجة والنجوم والشارات تُحسب
  كلها في قاعدة البيانات؛ المتصفح لا يرى الإجابة الصحيحة قبل أن تجيب الطالب.
  تحديث الصفحة في منتصف الاختبار يستأنف المحاولة نفسها.
- **عند المعلم**: قسم «نتائج اختبر» (آخر نتيجة، عدد المحاولات، أفضل نتيجة، من لم
  تجرِ الاختبار، المهارات الأضعف) + نافذة تفاصيل بأخطاء آخر محاولة، وسطر جديد في
  «عرض التقدم» لكل طالب.
- **النجوم**: عدد الإجابات الصحيحة، لكن **لأول اختبار مكتمل في اليوم فقط** (بتوقيت
  مسقط) حتى لا تتحول الإعادة إلى تجميع نجوم. لتغيير الحد عدّلي
  `v_daily_star_attempts` في `complete_quiz_attempt`. شارتان جديدتان:
  «بنّاءة البرج» و«برج كامل».
- **لوحة النجوم المرحة**: زر «نجمة» واضح على بطاقة كل طالب، «إضافة كل الطلاب»
  بضغطة واحدة، مراكز أول ثلاث، «رتّب حسب النجوم»، وتأكيد قبل حذف بطاقة. والتعديل
  صار ذرّيًا داخل قاعدة البيانات (`adjust_star_board_stars`) فلا تضيع نجمة عند
  النقر السريع أو فتح اللوحة على جهازين.
- **تحصين «اكتشف»**: `record_placement_answer` كانت تسمح بإعادة الإجابة على السؤال
  نفسه وبسؤال أي رقم سؤال من البنك، فيمكن استخراج الإجابات الصحيحة. أُغلق الأمران.

**كيف أفعّلها**
1. في SQL Editor شغّل `supabase/schema.sql` كاملًا (أو `phase2-quiz-and-stars.sql`
   وحده إن كانت المرحلة الأولى تعمل عندك).
2. شغّل `supabase/quiz_smoke_test.sql` — يجب أن يطبع «نجح الاختبار: تم فحص ٤٠٠٠
   سؤالًا بلا أي خطأ»، وأن يعرض الاستعلام الأخير `false | false | false`.
3. `npm run build` ثم جرّب بحساب طالب: `/quiz` ← أكمل الاختبار ← افتح لوحة
   المعلم وانظر قسم «نتائج اختبر».

> ⚠️ عمود الإجابة الصحيحة في `quiz_attempt_questions` محجوب بصلاحيات الأعمدة، فلا
> تستعمل `select("*")` على هذا الجدول من الواجهة — اذكري الأعمدة صراحةً.

## 🎮 المرحلة الثالثة — ألعاب «ألعب»: مغامرة الجمع ومغامرة الطرح

**ما الجديد**
- لعبتان فرديتان بمحرّك مشترك (`pages/GamePage.tsx` + `components/play/*`)، لا تعرفان
  شيئًا عن بعضهما — الفرق كله في `data/playGameThemes.ts` (الاسم، الألوان،
  الشخصية، العبارات). إضافة لعبة ثالثة لاحقًا بنفس شكل «سؤال فأربع خيارات» لا
  تحتاج صفحة جديدة، فقط ثيمًا + صفًا في `play_games` + بنك أسئلة.
- تصميم مختلف عمدًا عن «اختبر»: شخصية متحركة (`Mascot.tsx`) تبتسم/تتمايل حسب
  الإجابة، فقاعات إجابة ملوّنة بدل شبكة رمادية، شريط عشر جواهر بدل برج الطوب،
  وأصوات أكثر مرحًا (`lib/playSounds.ts`، على نفس محرك `lib/sound.ts`).
- عشرة أسئلة تتصاعد صعوبتها داخل الجولة: ٣ سهلة (خانة واحدة) ثم ٤ متوسطة
  (خانتان + خانة) ثم ٣ صعبة (خانتان + خانتان).
- نفس نظام «اختبر» بالضبط من ناحية الأمان: المحاولة والأسئلة والإجابة الصحيحة
  والنتيجة كلها في قاعدة البيانات عبر دوال `SECURITY DEFINER`
  (`start_game_attempt` / `record_game_answer` / `complete_game_attempt`)،
  ولا يرى المتصفح `answer_key` قبل الإجابة (محجوب بصلاحيات الأعمدة). تحديث
  الصفحة في منتصف اللعبة يستأنف نفس المحاولة. اللعب غير محدود (لا مهلة يومية)
  والمعلم لا تبدأ اللعبة، فقط تتابع النتائج.
- بنك الأسئلة (`supabase/game_bank.sql`, ٢٦٤ سؤالًا) مُولَّد آليًا بسكربت حتمي
  (`scripts/generate-game-bank.mjs`) ومفحوص ببرنامج مستقل
  (`scripts/verify-game-bank.mjs`) يتأكد رياضيًا أن الجمع بلا حمل والطرح بلا
  استلاف والخيارات صحيحة — ثم يعيد `game_smoke_test.sql` نفس الفحص داخل قاعدتك.
  القيد `game_questions_math_ok` في قاعدة البيانات يرفض أي سؤال سيئ حتى لو أُضيف
  يدويًا لاحقًا.
- النقاط/النجوم من هذه الألعاب **مستقلة تمامًا** عن نجوم «اختبر» ولوحة النجوم
  المرحة: كتالوج `play_games.reward_stars` (=٠ الآن لكل لعبة، فلا نجوم تُمنح
  حاليًا). لتفعيل مكافأة لعبة لاحقًا: `update public.play_games set
  reward_stars = 2, reward_min_percentage = 70 where id = 'addition';` — تُمنح
  حينها مرة واحدة في اليوم لكل لعبة (بتوقيت مسقط)، بنفس منطق «اختبر».
- عند المعلم: قسم «نتائج الألعاب» بتبويب بين اللعبتين (آخر نتيجة، عدد
  المحاولات، أفضل نتيجة، من لم تلعب)، ونافذة تفاصيل (الدقة حسب مستوى الصعوبة،
  تطور المحاولات، أخطاء آخر محاولة). وسطر جديد في «عرض التقدم» لكل طالب.
- الطالب ترى اللعبة في «آخر نشاط» في رئيسيتها.

**التعديل الوحيد على ملف قائم خارج المرحلة (تكامل ضروري)**
- `components/practice/GameCard.tsx`: بطاقتا «الجمع» و«الطرح» في «ألعب» تفتحان
  الآن صفحة داخلية (`/play/addition`, `/play/subtraction`) بدل البحث عن ملف
  HTML خارجي في `public/games/`. الأقسام الستة الأخرى في «ألعب» (لم تُطلب في
  هذه المرحلة) لم تُمس ولا تزال تعمل بالآلية القديمة.

**كيف أفعّلها**
1. في SQL Editor شغّل `supabase/schema.sql` كاملًا. أو، على قاعدة تعمل فيها
   المرحلتان الأولى والثانية: شغّل `supabase/phase3-play-games.sql` ثم
   `supabase/game_bank.sql` (بهذا الترتيب).
2. شغّل `supabase/game_smoke_test.sql` — كل الاستعلامات الأولى يجب أن تُرجع

3. (اختياري) للتأكد محليًا قبل النشر: `node scripts/generate-game-bank.mjs`

> ⚠️ عمود الإجابة الصحيحة في `game_attempt_questions` محجوب بصلاحيات الأعمدة،

## ⭐ تحديث المرحلة الثالثة — نجوم، اتجاه عربي، ولعبتان جديدتان

**النجوم (تغيير مهم عن التصميم الأول)**
- كل لعبة تمنح نجومًا الآن، لكن **مرة واحدة فقط طوال عمر الطالب في كل لعبة** —
  أول محاولة مكتملة فقط، مهما كانت نتيجتها. أي محاولة ثانية أو عاشرة، ومهما
  كانت مثالية، لا تمنح نجومًا أبدًا. هذا **يختلف عن «اختبر»** الذي يمنح نجومًا
  يوميًا.
- عدد النجوم = عدد الإجابات الصحيحة في تلك المحاولة الأولى (٠ إلى ١٠) — بلا حد
  أدنى للنسبة، فالمحاولة الأولى دائمًا تُكافأ بمقدار ما أنجزت فيها الطالب.
- كل لعبة مستقلة عن الأخرى: أول محاولة في «الجمع» وأول محاولة في «الطرح»
  تُكافآن كلتاهما، كل واحدة على حدة.
- التحكم عبر عمودين في `play_games`: `reward_enabled` (مفعّل للجميع الآن)
  و`reward_min_percentage` (=٠ لكل الألعاب حاليًا، أي بلا شرط). لتغيير لعبة
  لاحقًا: `update public.play_games set reward_min_percentage = 50 where id =
  'rounding';`.

**اتجاه عرض السؤال (إصلاح)**
- كانت مسائل الجمع/الطرح تُعرض بالاتجاه الغربي (الجواب في أقصى اليمين). أُصلح
  لتُقرأ بالاتجاه العربي كبقية المنصة: العدد الأول يمينًا، وعلامة الاستفهام أو
  الجواب في أقصى اليسار.

**لعبتان جديدتان: مغامرة التقريب ومغامرة الضعف**
- **مغامرة التقريب** (`rounding`): عشرة أسئلة تصاعدية — ٣ أسهل (عدد من خانتين
  لأقرب عشرة) ثم ٤ متوسطة (ثلاث خانات لأقرب عشرة) ثم ٣ أصعب (ثلاث خانات لأقرب
  مئة). تصميم مختلف تمامًا: **خط أعداد** بين الحدّين، ومنطاد يحمل العدد فوق
  موضعه الحقيقي، وشخصية نجمة زرقاء.
- **مغامرة الضعف** (`doubling`): عشرة أسئلة — ٣ أسهل (رقم واحد ١–٩) ثم ٤
  متوسطة (رقمان ١٠–٤٩) ثم ٣ أصعب (ثلاث أرقام ١٠٠–٤٩٩)، بحيث لا يتجاوز ناتج
  الضعف عدد خانات المُدخل نفسه («سهلة للأطفال» كما طُلب). تصميم مختلف: **جراب
  ينقسم إلى جرابين متطابقين**، وشخصية غيمة وردية بفيونكة.
- كلتاهما تعيدان استخدام محرّك اللعب نفسه (`GamePage.tsx`) ونظام الأمان نفسه
  (RLS، حجب الإجابة الصحيحة، الاستئناف بعد تحديث الصفحة) — الاختلاف كله في
  `data/playGameThemes.ts` (الثيم) ومكوّني الرسم الجديدين
  `NumberLineVisual.tsx` و`DoublingVisual.tsx`.
- بنك الأسئلة كبر من ٢٦٤ إلى **٤٩٣ سؤالًا** (التقريب ٣٦/٤٨/٤٨، الضعف ٩/٤٠/٤٨ —
  الضعف الأسهل له ٩ قيم ممكنة فقط رياضيًا: الأعداد ١ إلى ٩).

**كيف أطبّق هذا التحديث**
1. شغّل `supabase/schema.sql` كاملًا من جديد (أو `phase3-play-games.sql` ثم
   `game_bank.sql` بهذا الترتيب) — كله `CREATE OR REPLACE` / `ALTER ... IF NOT
   EXISTS` آمن التكرار، ولا يحذف بيانات موجودة. إن كانت لديك بيانات محاولات
   قديمة من النسخة الأولى فستبقى كما هي.
2. شغّل `supabase/game_smoke_test.sql` المحدَّث — يفحص الآن أربع ألعاب بدل
   اثنتين، ويتأكد أن `reward_enabled = true` و`reward_min_percentage = 0` لكل
   الألعاب.
3. `npm run build` ثم جرّب: العب «التقريب» أو «الضعف» مرتين بنفس الحساب،
   وتأكد أن النجوم تُمنح في الأولى فقط.

**لأمانة النقل: خطآن وجدتهما بالاختبار الفعلي قبل التسليم، لا بالقراءة فقط**
- مولّد بنك أسئلة التقريب كان ينتج خيارات مختلطة النوع (بعضها رقم JS خام
  وبعضها نص) بسبب سطر ناقص فيه `.map(String)`. لم يكن هذا يخالف قيود قاعدة
  البيانات (فتشغيل `game_smoke_test.sql` وحده ما كان سيكشفه)، لكنه كان يعطّل
  حفظ إجابة الطالب فعليًا عند اختيار أحد هذين الخيارين تحديدًا. أصلحته
  ووسّعت `verify-game-bank.mjs` بفحص صارم لنوع كل خيار حتى لا يتكرر.
- دالة تحليل الرسم البصري في `lib/games.ts` كانت تعرف نوع "expression" فقط
  فتُسقط بيانات التقريب والضعف بصمت وتعرضهما كمعادلة جمع فارغة. أُصلحت.

**ما لم يتغيّر:** كل ما في «اكتشف» و«اختبر» ولوحة النجوم المرحة والجمع والطرح
(الأسئلة، القواعد الرياضية) كما هو تمامًا.

## 🔧 إصلاح عاجل — «مغامرة التقريب/الضعف» تقول «حاول مرة أخرى»

**السبب:** إن كنت شغّلت نسخة `schema.sql` قبل هذا التحديث (نسخة الجمع والطرح
فقط)، فجدولا `game_questions` و`game_attempt_questions` أصبحا موجودين بالفعل
بقيود قديمة (الأرقام حتى ٩٩ فقط، `operand_b` إلزاميًا، العمليات `+`/`-` فقط).
أمر `create table if not exists` في `schema.sql` **لا يلمس جدولًا موجودًا**،
فتبقى تلك القيود القديمة وتمنع إدخال أسئلة التقريب والضعف — وهذا بالضبط ما
يسبب «حاول مرة أخرى». هذا خطأ مني في الملف الذي سلّمته سابقًا، وجدته بعد
مراجعة الملف سطرًا سطرًا بعد بلاغك.

**الإصلاح — أسرع طريق (دقيقة واحدة):**
1. شغّل `supabase/fix_rounding_doubling_migration.sql` (ملف جديد، مستقل، آمن
   ولا يحذف بيانات). آخر سطر فيه استعلام تأكيد: يجب أن يُظهر `has_new_constraint
   = 1` و`operand_b_nullable = YES`.
2. شغّل `supabase/game_bank.sql` بعده مباشرة.
3. جرّب «مغامرة التقريب» مجددًا.

(أو الأبسط: أعد تشغيل `supabase/schema.sql` كاملًا من هذا التحديث — يحتوي
نفس الإصلاح مدمجًا، ويعمل سواء كانت الجداول موجودة من قبل أو لا.)

**ملاحظة للشفافية:** هذا النوع من الأخطاء — ترقية جدول *موجود بالفعل* بقيود
جديدة — لا يستطيع اختباري الآلي (الذي يحاكي قاعدة البيانات بجافاسكريبت بلا
PostgreSQL حقيقي) اكتشافه، لأنه لا يحاكي حالة "قاعدة قديمة تُرقَّى" بل ينشئ
قاعدة جديدة نظيفة في كل مرة. لهذا فاتني هذا الخطأ رغم أن كل اختباراتي كانت
ناجحة. راجعت الملف كاملًا سطرًا بسطر يدويًا بعد بلاغك ووجدت الخلل وأصلحته.


## وضع التدشين / التجربة (المرحلة العاشرة)

زرّا «🧑‍🏫 تجربة المعلم» و«🧒 تجربة الطالب» في صفحة الدخول يُدخلان إلى **بنيان الحقيقي نفسه** بحسابات وبيانات تجريبية: حسابات Supabase Auth حقيقية (معلم + ٦ طلاب لكل «Slot») تعمل على نفس الجداول والدوال وRLS. العزل بين المعلمات وعن الحسابات الحقيقية يأتي من الملكية في RLS كما في أي معلم حقيقية، لا من أي فرع `if (demo)` في الواجهة. شارة «🧪 وضع التجربة» و«الخروج من التجربة» تظهر للجلسات التجريبية فقط.

**الملفات:** `supabase/phase10-demo-mode.sql` (جداول مغلقة + دوال + تعبئة عبر دوال النظام الحقيقية) · `supabase/functions/demo-start` و`demo-sweep` و`_shared/demo.ts` · `src/lib/demo.ts` · `src/components/DemoBadge.tsx` · `scripts/probe-demo-auth.mjs` · `scripts/demo-security-tests.sql` · `supabase/phase10b-demo-caps.sql` (اختياري).

**خطوات التفعيل (بالترتيب، مرة واحدة):**
1. `npm run build` ينجح.
2. شغّل `scripts/probe-demo-auth.mjs` محليًا (يتطلب مفتاح service-role من جهازك فقط) وتأكد أن النتيجة ✅. ينشئ مستخدمًا مؤقتًا ويحذفه.
3. شغّل `supabase/phase10-demo-mode.sql` في SQL Editor.
4. انشر **بهذه الأوامر تحديدًا**: `supabase functions deploy demo-start --no-verify-jwt` و`supabase functions deploy demo-sweep --no-verify-jwt` و`supabase functions deploy create-student`. الخيار `--no-verify-jwt` ضروري للدالتين العامتين: مفاتيح المشاريع الجديدة (`sb_publishable_…`) ليست JWT فترفضها البوابة بخطأ 401. (الدالتان تتحققان بنفسيهما: demo-start تقبل الدور فقط، وdemo-sweep تتطلب مفتاح service-role.) وللتشخيص: `node scripts/diagnose-demo.mjs`.
5. فعّلي التجربة: `update public.demo_settings set enabled = true;` (الافتراضي معطّل فلا يظهر أي زر).
6. راجع Auth → Rate Limits وارفعي حدود الدخول/التحقق مؤقتًا يوم التدشين (معلمات المدرسة قد يشتركن في IP واحد).
7. شغّل `scripts/demo-security-tests.sql` وتأكد أن كل الصفوف PASS.

**دورة حياة الـSlot:** تُنشأ عند الطلب (مع مخزون دافئ صغير)، وتبقى ٩٠ دقيقة بعد آخر نشاط (نبضة كل ٥ دقائق) وبحد أقصى ١٢ ساعة، ثم تُحذف بالكامل: مستخدموها (فتُحذف مسابقاتهم ونتائجهم بالتتالي) وملفات Storage وأي طلاب أضافتهم معلم التجربة، ثم يُنشأ Slot جديد بمعرّفات جديدة (فلا تبقى جلسة قديمة صالحة). للتنظيف الدوري استدعي `demo-sweep` بـ`Authorization: Bearer <service-role>` (يمكن جدولته بـpg_cron + pg_net)، ولإنهاء كل التجارب بعد التدشين: `{"action":"teardown_all"}` ثم `update public.demo_settings set enabled = false;`.

**المسابقات — موارد السؤال (9b):** يمكن إرفاق صورة/فيديو/PDF/رابط بالسؤال نفسه (يظهر للمشارك فوق نص السؤال). يلزم تشغيل `supabase/phase9b-competition-attachments.sql` مرة واحدة بعد `phase9-competitions.sql` حتى يستطيع الزائر قراءة ملفات المرفقات المرفوعة.

**ملاحظة (v37):** إن فشل تجهيز Slot في تجارب سابقة فقد بقي مستخدمون تجريبيون يتامى؛ نظّفيهم بـ`supabase/demo-cleanup-orphans.sql` (معاينة أولًا ثم حذف اختياري). بعد أي تعديل على `supabase/functions/_shared/demo.ts` أعد نشر `demo-start` و`demo-sweep` معًا لأنهما تشتركان فيه.
